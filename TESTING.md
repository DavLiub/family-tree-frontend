# Проверки интерфейса

Автоматические наборы запускаются в GitHub Actions. На VPS не запускать их без прямого поручения пользователя. Команды ниже предназначены для CI или отдельно разрешённой среды разработки. Используются только вымышленные данные из `test/fixtures/`, без настоящих токенов, семейных экспортов и адресов рабочего API.

## Наборы

| Слой | Команда | Область |
|---|---|---|
| Unit | `npm test` | Существующие `test/unit/**/*.test.js`, happy-dom, coverage v8 |
| Frontend integration | `npm run test:integration` | `test/integration/**/*.test.js`, реальные appState/Auth/api и управляемый fetch |
| UI smoke (PR) | `npm run build`, затем `npm run test:ui:smoke` | Все UI-сценарии на desktop 1440×900 |
| UI DOM/layout | `npm run build`, затем `npm run test:ui` | Chromium, production `dist`, desktop 1440×900 и touch/mobile 390×844 |

Integration использует отдельный `vitest.int.js`; include каждого Vitest-набора задан явно, поэтому Playwright specs не исполняются Vitest и integration не попадает в unit coverage. Конфигурация интеграции наследует happy-dom и существующую обработку ESM-зависимости, но заменяет include без объединения массивов.

Интеграционные сценарии проверяют границы настоящих модулей: авторизованную запись и db:changed; ошибку прав и завершение счётчика сохранения; запрет записи после смены дерева другой вкладкой; изменение имени с ошибкой и повторной попыткой; поиск, где новый ответ приходит раньше старой ошибки HTTP. Подменяется fetch, а не appState/api/Auth. Навигационные тесты сохраняют реальный Lit lifecycle и методы view, заменяя только render дочерних виджетов. Это **frontend integration**, не проверка серверного контракта, реального backend RBAC, БД или восстановления данных.

Unit-регрессии навигации переставляют порядок ответов карточки/поиска, проверяют актуальность данных, ошибок и loading, очистку/уход со страницы, сброс пагинации и кодирование query. Управляемые Promise задают порядок завершения запросов; произвольные задержки не заменяют проверку результата.

## Изолированный UI

CI устанавливает Chromium командой `npx playwright install --with-deps chromium`. `playwright.config.js` поднимает `node scripts/ui-server.mjs`; сервер слушает только `127.0.0.1:4173`, отдаёт файлы только из dist и разрешённые SPA-маршруты. API на сервере всегда отвечает 503, никакого proxy/настоящего backend нет. Запуск требует предварительной сборки; существующий сервер не переиспользуется.

Playwright context.route перехватывает сеть до навигации: разрешены только GET локальных статических ресурсов и явно описанные синтетические API-ответы. Остальные API, внешние домены и неожиданные методы блокируются и проваливают тест. Единственный специальный POST для неавторизованного запуска `/api/token/create_owner/` получает синтетический отказ 405; POST переводов получает тождественные английские строки. Они не доходят до сервера. Синтетический неподписанный JWT проверяется только клиентом; никаких настоящих паролей нет. Service workers заблокированы, чтобы не обходить route.

UI проверяет доступные имена/поля входа, видимость отправки, заголовок карточки и действие дерева, переход по breadcrumb к списку, объяснение пустого дерева и выход из него. Проверяется отсутствие горизонтального переполнения документа на 1440 и 390 px. Сценарий имени отдельно разрешает только синтетический PUT: задержка, ошибка, сохранение ввода, блокировка повторной отправки и успешная повторная попытка. Реальные записи и удаление не выполняются. Для Material Web состояние disabled проверяется на host, видимость модального окна — по роли dialog, slotted поля/сообщения ищутся от компонента формы. Ошибки JS и неожиданные запросы проверяются после каждого сценария. Отсутствие реального backend не означает, что эти проверки подтверждают серверные права.

Нет пиксельных эталонов и screenshot snapshots. Trace сохраняется только при ошибке, screenshot — only-on-failure; HTML-отчёт и test-results служат диагностике CI и не должны попадать в Git. При сбое смотреть сначала unexpected requests/pageerror и данные фикстуры; не расширять mock произвольным `[]` для всех API и не отключать assertions для зелёного результата.

## Известные ограничения

- На текущем входе при viewport 320 px в ревью 008 измерена ширина документа 354 px. Исправление интерфейса не входит в этот CI PR. Проверка 320 px не добавлена как skipped/disabled test: заявленная baseline этого набора — 390 и 1440. После отдельного исправления следует добавить 320 как полноценный проект и проверку overflow.
- Это Chromium с эмуляцией touch, не физический телефон, Safari/WebKit или Firefox. Проверки поведения реальных экранных клавиатур и жестов остаются ручными.
- UI не проверяет интерактивную диаграмму с несколькими поколениями, полный маршрут поиска/родственников, PDF, RU-локализацию и серверный API. Ошибки сохранения покрыты пока только для имени. Расширять сценарии отдельными задачами с содержательными фикстурами.
- До первого запуска в CI результаты новых наборов неизвестны. Статические проверки конфигурации не заменяют исполнение.

## Архитектурные проверки

Отдельный слой guards описывается в `GUARDS.md` и выполняется независимо от функциональных наборов. Их успешность не доказывает корректность пользовательского поведения; функциональные наборы не заменяют guards.

## GitHub Actions

Workflow `.github/workflows/test.yml` запускается на `pull_request`, push только в `main` и вручную (`workflow_dispatch`). Push рабочей ветки не создаёт повторный CI; до открытия PR автоматической проверки этой ветки нет. Ручной запуск доступен для выбранной ветки.

| Этап | UI | Критерий завершения |
|---|---|---|
| PR | `UI smoke (PR)`: все текущие сценарии на desktop | Зелёный `CI gate` последнего коммита PR |
| Push main после merge | `UI regression (full)`: весь набор desktop + mobile | Зелёный `CI gate` merge-коммита main |
| Ручной запуск | Полный набор desktop + mobile | Зелёный `CI gate` выбранного запуска |

Оба этапа также выполняют статические проверки/сборку, Unit and integration и Architecture guards. Мобильная UI-регрессия после merge может обнаружить проблему уже в main; это требует исправления отдельным PR. Зелёный PR означает прохождение проверки до merge; состояние main оценивается отдельно. Набор smoke выбирается по Playwright project `desktop`, поэтому новые UI-сценарии автоматически входят в PR на desktop.

Установка Chromium и системных зависимостей имеет отдельный таймаут 4 минуты, исполнение Playwright — общий лимит 3 минуты при сохранённом лимите 30 секунд на сценарий. Действующий лимит UI job — 15 минут с учётом npm ci, подготовки и загрузки отчётов; это не обещание времени исполнения. Зависание установки будет ошибкой подготовки окружения, а не падением assertion теста. Текущая установка браузера остаётся сетевой; её ускорение не гарантируется.

UI получает dist из артефакта текущего запуска; отдельный обязательный `CI gate` завершается успешно только при success всех групп и сборки. Провал/пропуск/отмена зависимого job не превращается в зелёный gate. Есть таймауты, отмена устаревших запусков, read-only permissions и закреплённые SHA Actions. Сайт не публикуется.

Защита main отдельно настроена в GitHub: PR и актуальный зелёный CI gate, без обязательного второго ревьюера; force push и удаление запрещены. По решению владельца административный обход сохранён. Одного YAML недостаточно для воспроизведения этих настроек в другом репозитории. Изменения тестов проверяются новым CI после commit/push.
